# 📝 Understand Log Analysis

> **"Logs are the memory of a system. They record what happened, when it happened, and often which user, process, or service was involved."**

---

# 📖 What is Log Analysis?

**Log analysis** is the process of collecting, reading, filtering, and investigating system logs to understand events occurring on a computer or network.

Logs can help answer:

```text
What happened?
     ↓
When did it happen?
     ↓
Who or what caused it?
     ↓
Was it normal or suspicious?
     ↓
What should be done?
```

In cybersecurity, logs are important for:

- 🔍 Threat detection
- 🚨 Incident investigation
- 👤 Tracking authentication activity
- ⚙️ Troubleshooting services
- 🕵️ Finding suspicious behavior
- 📋 Creating evidence and timelines

---

# 🖥️ A. System Logs

## 📖 What are System Logs?

**System logs** contain records generated by the operating system and its components.

They can record events such as:

- System startup/shutdown
- Hardware events
- Kernel messages
- Service activity
- Errors
- Warnings
- System failures

On many Linux systems, logs can be accessed through:

```bash
journalctl
```

Traditional log files may also exist under:

```text
/var/log/
```

---

## 🔍 Viewing System Logs

View the system journal:

```bash
journalctl
```

View recent entries:

```bash
journalctl -n 50
```

View logs from the current boot:

```bash
journalctl -b
```

Follow new log entries:

```bash
journalctl -f
```

---

# 📁 Important Log Locations

The exact files vary between Linux distributions and logging configurations.

Common examples include:

```text
/var/log/
├── auth.log
├── syslog
├── kern.log
├── boot.log
└── apache2/
```

On some distributions, authentication and system events may instead be stored in:

```text
/var/log/secure
```

or primarily in the systemd journal.

---

# 👤 B. Authentication Logs

## 📖 What are Authentication Logs?

**Authentication logs** record events related to users attempting to authenticate to the system.

They may contain information about:

- Successful logins
- Failed login attempts
- SSH authentication
- `sudo` usage
- User sessions
- Account-related events

---

## 🔐 Why are Authentication Logs Important?

Authentication logs can reveal:

```text
Normal Login
      │
      ▼
Expected user + expected time
```

versus:

```text
Suspicious Login
      │
      ▼
Unknown account
      │
      ▼
Repeated failures
      │
      ▼
Successful login
      │
      ▼
Possible compromise
```

A single failed login is usually not enough to indicate an attack.

A large number of failures followed by a successful login may deserve investigation.

---

# 🔍 Searching Authentication Logs

On systems using traditional authentication logs:

```bash
grep "Failed password" /var/log/auth.log
```

Successful SSH authentication may be searched with:

```bash
grep "Accepted" /var/log/auth.log
```

On systems using the journal:

```bash
journalctl -u ssh
```

The exact service name can differ by distribution.

---

# ⚙️ C. Service Logs

## 📖 What are Service Logs?

Services often generate their own logs describing what they are doing.

Examples:

- SSH
- Web servers
- Databases
- DNS servers
- Firewalls
- Applications

These logs can contain:

- Connections
- Errors
- Requests
- Authentication events
- Configuration problems
- Service failures

---

## 🌐 Example: Web Server

A web server might record:

```text
Client IP
Requested URL
HTTP method
Response status
Timestamp
User agent
```

Example:

```text
192.168.1.20 - GET /login - 200
```

This means a client requested `/login` and received HTTP status `200`.

---

# 🔍 Investigating a Service

For a systemd-managed service:

```bash
systemctl status ssh
```

View its journal:

```bash
journalctl -u ssh
```

Follow new entries:

```bash
journalctl -u ssh -f
```

For another service:

```bash
journalctl -u nginx
```

---

# 🕵️ D. Log Investigation

## 📖 What is Log Investigation?

**Log investigation** means examining logs to determine whether an event is normal, suspicious, or malicious.

A good investigation looks at:

```text
Timestamp
   ↓
Source
   ↓
User
   ↓
Action
   ↓
Result
   ↓
Related Events
```

---

# 🕐 1. Start With the Timeline

Time is extremely important.

Suppose:

```text
10:01 → Multiple failed logins
10:03 → Successful login
10:05 → New process starts
10:06 → Outbound network connection
10:08 → Sensitive file modified
```

Individually, these events may not prove an attack.

Together, they create a potentially suspicious sequence.

---

# 👤 2. Identify the User

Ask:

- Which account was involved?
- Is the account expected?
- Is it an administrator?
- Was the account normally active at that time?

Example:

```text
User: backup
```

If the `backup` account suddenly performs interactive SSH logins, that may require investigation.

---

# 🌐 3. Identify the Source

Look for:

- Source IP
- Hostname
- Local/remote origin
- Application
- Process

Example:

```text
Failed SSH login
Source: 203.0.113.50
User: admin
```

Repeated attempts from the same source may indicate password-guessing activity.

---

# 🔎 4. Search for Patterns

Instead of reading thousands of log lines manually, use command-line tools.

### `grep`

```bash
grep "Failed" /var/log/auth.log
```

### Count matching lines

```bash
grep -c "Failed" /var/log/auth.log
```

### Search multiple terms

```bash
grep -Ei "failed|invalid|error" logfile.log
```

### View recent logs

```bash
journalctl -n 100
```

---

# 🔗 5. Correlate Multiple Logs

One log source rarely tells the entire story.

For example:

```text
Authentication Log
        │
        ▼
Successful Login
        │
        ▼
System Log
        │
        ▼
New Process
        │
        ▼
Service Log
        │
        ▼
Unexpected Request
        │
        ▼
Network Activity
```

Combining these events creates a much clearer picture.

---

# 🚨 E. Security Indicators

## 📖 What is a Security Indicator?

A **security indicator** is an observation that may suggest suspicious or malicious activity.

It does **not automatically prove that an attack occurred**.

Examples include:

- Repeated failed authentication
- Unexpected successful login
- Unknown user account
- Unusual login time
- Unexpected privilege escalation
- Suspicious process creation
- Unexpected service changes
- Large numbers of errors
- Unusual outbound connections
- Important files being modified

---

# 🔥 Example: Brute-Force Indicator

Imagine the logs contain:

```text
Failed login from 203.0.113.10
Failed login from 203.0.113.10
Failed login from 203.0.113.10
Failed login from 203.0.113.10
Failed login from 203.0.113.10
Successful login from 203.0.113.10
```

This pattern is suspicious.

The analyst should investigate:

```text
Who logged in?
      ↓
Was the login legitimate?
      ↓
What happened after login?
      ↓
Were privileges changed?
      ↓
Were files modified?
      ↓
Were network connections created?
```

---

# 🧪 Real-World Incident Example

Imagine a Linux web server suddenly starts behaving strangely.

The investigation finds:

```text
1️⃣ Multiple failed SSH logins
          ↓
2️⃣ Successful login to an administrator account
          ↓
3️⃣ New process appears
          ↓
4️⃣ New outbound network connection
          ↓
5️⃣ Web server configuration modified
```

The individual events are useful.

But their **relationship and sequence** are much more important.

This is why security analysts perform **log correlation** rather than looking at isolated entries.

# 🛠️ Useful Log Analysis Commands

| Command | Purpose |
|---|---|
| `journalctl` | View systemd journal |
| `journalctl -f` | Follow new log events |
| `journalctl -b` | Logs from current boot |
| `journalctl -u service` | Logs for a service |
| `grep` | Search log contents |
| `less` | Read large logs |
| `tail` | View the end of a log |
| `head` | View the beginning |
| `wc` | Count lines/words |
| `sort` | Sort results |
| `uniq` | Find/count repeated entries |

---

# 🔗 Combining Commands

Linux commands become more powerful when combined.

Example:

```bash
grep "Failed password" /var/log/auth.log | sort | uniq -c
```

Conceptually:

```text
Authentication Log
       ↓
Find failed passwords
       ↓
Sort results
       ↓
Count repeated entries
```

This can help reveal repeated authentication failures.

# 🧠 Log Analysis Workflow

A simple investigation workflow:

```text
       🚨 Suspicious Event
              │
              ▼
        Collect Logs
              │
              ▼
       Filter Relevant Data
              │
              ▼
       Check Timestamps
              │
              ▼
     Identify Users / Sources
              │
              ▼
       Correlate Events
              │
              ▼
      Determine Normal vs
          Suspicious
              │
              ▼
       Investigate Further
              │
              ▼
       Document Findings
```

# ⚖️ Normal vs Suspicious Logs

Not every unusual event is malicious.

| Event | Possible Explanation |
|---|---|
| Failed login | User entered wrong password |
| Many failed logins | Password attack or misconfigured application |
| High CPU | Legitimate workload or malware |
| New service | Software installation or persistence |
| Large log file | Heavy legitimate activity or log flooding |
| Unknown IP | Legitimate remote user or suspicious connection |

**Context matters.**

---

# 🛡️ Logs and Incident Response

Logs are useful during multiple stages of incident response:

```text
Detection
   ↓
Investigation
   ↓
Containment
   ↓
Recovery
   ↓
Lessons Learned
```

For example, logs can help determine:

- When the incident started
- Which account was involved
- Which systems were affected
- What actions occurred
- Whether suspicious activity continued

---

# 📊 Log Analysis vs Log Monitoring

| Log Monitoring | Log Analysis |
|---|---|
| Watches logs as they arrive | Examines log information |
| Often real-time | Can be real-time or historical |
| Detects events | Investigates meaning |
| Often automated | Can involve human investigation |
| Alerts on patterns | Correlates and explains events |

Modern organizations often use **SIEM platforms** to collect, normalize, correlate, search, and alert on logs from many systems.

# 🧠 Memory Trick

Think of logs as a **CCTV recording for a computer**:

- 🕐 Timestamp = When
- 👤 User = Who
- 🌐 IP = Where from
- ⚙️ Process/Service = What was involved
- 📝 Event = What happened
- 🔗 Correlation = How events are connected

One camera recording may not explain everything.

Multiple recordings together can reveal the complete story.

# 💡 Interview Tips

### ❓ Why are logs important in cybersecurity?

Logs provide evidence of system activity and help security professionals detect, investigate, and understand security incidents.

### ❓ What is log correlation?

**Log correlation** means connecting events from different logs or systems to identify relationships and understand a larger security incident.

### ❓ Does a failed login mean an attack?

No. A single failed login can be completely normal. Repeated failures, unusual sources, unusual times, and successful access afterward may make the activity more suspicious.

### ❓ Where are Linux logs stored?

Many Linux systems use the **systemd journal**, accessible with `journalctl`. Traditional log files are also commonly found under:

```text
/var/log/
```

The exact location depends on the Linux distribution and logging configuration.

>

>
> 🚨 **Security indicators provide clues—but context is required to determine whether activity is actually malicious.**
