# 📊 Security Logging & Monitoring

> **Security logging and monitoring is the process of recording important system and application events, analyzing those events, and using them to detect, investigate, and respond to security incidents.**

A secure application should not only prevent attacks.

It should also help security teams answer:

```text
What happened?
When did it happen?
Who performed the action?
What was affected?
Where did it come from?
Was it successful?
What happened afterward?
```

A simple security visibility pipeline is:

```text
Application / Server / User
          ↓
       Logs
          ↓
   Collection
          ↓
     Analysis
          ↓
    Monitoring
          ↓
 Detection / Alert
          ↓
 Investigation
          ↓
 Response
```

The five areas in this topic are:

1. 📝 Application Logs
2. 🌐 Access Logs
3. ❌ Error Logs
4. 📋 Audit Trails
5. 👁️ Security Visibility

---

# 1️⃣ Application Logs

## 📝 What Are Application Logs?

**Application logs** are records generated by an application while it is running.

They help developers and security teams understand what the application is doing.

For example:

```text
2026-09-30 10:15:22 INFO User login successful user_id=104
2026-09-30 10:16:03 WARN Login failed username=farhan
2026-09-30 10:16:15 INFO Password reset requested user_id=104
```

A log event normally contains information such as:

```text
Timestamp
Severity
Event
User / Account
Source
Request ID
Result
Additional context
```

---

# 🎯 Why Application Logs Matter

Without logs:

```text
Attack
  ↓
Something happens
  ↓
No record
  ↓
Difficult investigation
```

With useful logs:

```text
Attack
  ↓
Event recorded
  ↓
Security team investigates
  ↓
Timeline reconstructed
  ↓
Response
```

Logs can help with:

* Troubleshooting
* Security monitoring
* Incident investigation
* Threat detection
* Auditing
* Debugging
* Forensics

---

# 📊 Log Levels

Applications commonly use severity levels.

| Level    | Meaning                                       |
| -------- | --------------------------------------------- |
| DEBUG    | Detailed development information              |
| INFO     | Normal application events                     |
| WARNING  | Something unusual or potentially problematic  |
| ERROR    | An operation failed                           |
| CRITICAL | Serious failure requiring immediate attention |

Example:

```text
DEBUG
Database query completed

INFO
User logged in

WARNING
Multiple failed login attempts

ERROR
Payment service unavailable

CRITICAL
Database connection unavailable
```

The exact logging levels depend on the logging framework.

---

# 🔐 Security-Relevant Application Events

An application may log:

```text
Login success
Login failure
Password reset
MFA event
Account creation
Permission change
Role change
Sensitive action
File upload
API authentication failure
Administrative action
```

For example:

```text
2026-09-30T10:30:42Z
WARN
event=login_failed
user_id=104
source_ip=192.0.2.10
```

This can later help identify patterns.

---

# ⚠️ What Should NOT Be Logged?

Logging too much information can itself create a security problem.

Avoid logging sensitive secrets such as:

```text
❌ Passwords
❌ API keys
❌ Private keys
❌ Session tokens
❌ Access tokens
❌ Authentication secrets
```

Instead of:

```text
password=MyPassword123
```

log:

```text
event=login_failed
user_id=104
```

### Security principle

> **Log enough information to investigate, but don't create unnecessary copies of sensitive information.**

---

# 🧱 Structured Logging

Instead of:

```text
User Farhan failed login from IP 192.168.1.20
```

structured logging might use JSON:

```json
{
  "timestamp": "2026-09-30T10:30:42Z",
  "level": "WARNING",
  "event": "login_failed",
  "user_id": 104,
  "source_ip": "192.168.1.20"
}
```

This is easier for machines to process.

```text
Application
    ↓
JSON Logs
    ↓
Log Collector
    ↓
SIEM
    ↓
Detection Rules
```

---

# 🐍 Python Example

Python provides a built-in `logging` module.

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s"
)

logging.info("Application started")
logging.warning("Login attempt failed")
logging.error("Database connection failed")
```

Example output:

```text
2026-09-30 10:30:42 INFO Application started
2026-09-30 10:31:02 WARNING Login attempt failed
2026-09-30 10:31:10 ERROR Database connection failed
```

This connects directly with the **Python logging and security automation** topics you previously studied.

# 2️⃣ Access Logs

## 🌐 What Are Access Logs?

**Access logs** record requests made to a web server or application.

A typical web request might look like:

```text
Client
  ↓
GET /login
  ↓
Web Server
  ↓
Application
```

The server can record information about that request.

Example:

```text
192.168.1.20 - - [30/Sep/2026:10:30:42]
"GET /login HTTP/1.1" 200 4210
```

Depending on configuration, access logs may include:

```text
IP address
Timestamp
HTTP method
Requested path
HTTP status
Response size
User-Agent
Referrer
Request duration
```

---

# 🔍 Understanding an Access Log

Example:

```text
192.168.1.20
"POST /login HTTP/1.1"
401
```

Breakdown:

```text
192.168.1.20
      ↓
Source IP

POST
      ↓
HTTP method

/login
      ↓
Requested endpoint

401
      ↓
Authentication failure / unauthorized response
```

A single event may not mean much.

But many events together can reveal a pattern.

---

# 🚨 Example: Brute-Force Pattern

Suppose logs show:

```text
10:00:01 POST /login 401
10:00:02 POST /login 401
10:00:03 POST /login 401
10:00:04 POST /login 401
10:00:05 POST /login 401
...
```

A monitoring system might detect:

```text
Many failed authentication attempts
            ↓
Same source
            ↓
Short time window
            ↓
Potential brute-force activity
```

Important:

> **A detection is an indicator for investigation, not automatically proof of an attack.**

---

# 📊 Access Log Analysis

Useful questions include:

```text
Which IPs generate the most requests?
Which endpoints receive unusual traffic?
How many 404 responses occurred?
How many authentication failures occurred?
Are requests coming from unexpected locations?
Are sensitive endpoints being probed?
```

---

# 🕵️ Example: Endpoint Enumeration

Suppose access logs contain:

```text
GET /admin
GET /backup
GET /.env
GET /config
GET /login
GET /api/users
```

A sequence like this may indicate someone is exploring the application's attack surface.

It does not by itself prove malicious intent, but it is useful security telemetry.

# 3️⃣ Error Logs

## ❌ What Are Error Logs?

**Error logs** record failures and exceptional conditions.

Examples:

```text
Database connection failed
Application exception
Invalid configuration
File access failure
API timeout
Internal server error
```

Example:

```text
2026-09-30 10:40:15 ERROR Database connection timeout
```

---

# 🧠 Why Error Logs Matter for Security

Errors can reveal:

```text
Application failures
Unexpected inputs
Attack attempts
Configuration problems
Service outages
Dependency failures
```

They can also help reconstruct what happened during an incident.

---

# 💥 Example: Application Error

A user requests:

```text
GET /api/profile/abc
```

The application expects an integer.

An error occurs:

```text
ValueError: invalid literal for int()
```

The application should not expose its complete internal stack trace to the user.

### ❌ Bad user-facing response

```text
Traceback...
/var/www/app/database.py
PostgreSQL connection...
Internal configuration...
```

### ✅ Better

```text
500 Internal Server Error
Request ID: 8f32ab
```

The detailed error can be recorded in protected server-side logs.

---

# 🔐 Error Logs and Information Disclosure

Poor error handling can expose:

```text
File paths
Database information
Framework versions
Internal hostnames
Source code
Environment variables
Stack traces
```

Therefore:

```text
User
 ↓
Generic error
```

while:

```text
Server
 ↓
Detailed protected log
```

---

# 📋 Error Log Example

```text
2026-09-30T10:45:10Z
ERROR
service=payment-api
event=database_timeout
request_id=8f32ab
duration_ms=5020
```

Notice that this provides useful investigation information without storing a password or database credential.

# 4️⃣ Audit Trails

## 📋 What Is an Audit Trail?

An **audit trail** is a record of important actions performed within a system.

It answers:

> **Who did what, when, and to which resource?**

Example:

```text
User: admin01
Action: DELETE
Resource: user_account
Resource ID: 104
Timestamp: 2026-09-30 10:50:20
Result: SUCCESS
```

---

# 🆚 Logs vs Audit Trails

They overlap, but their purposes can differ.

| Logs                   | Audit Trail                         |
| ---------------------- | ----------------------------------- |
| Broad record of events | Focused record of important actions |
| Troubleshooting        | Accountability                      |
| Performance monitoring | Compliance/governance               |
| Errors                 | Administrative/security actions     |
| Application behavior   | Who did what                        |

An audit trail can be implemented using logs, but it usually focuses on actions that need strong accountability.

---

# 🔐 Important Audit Events

Examples:

```text
User created
User deleted
Role changed
Permission changed
MFA enabled/disabled
Password reset
Configuration changed
Security policy changed
Sensitive record accessed
Data exported
Administrative action
```

Example:

```json
{
  "timestamp": "2026-09-30T11:00:00Z",
  "actor": "admin01",
  "action": "role_changed",
  "target_user": "user104",
  "old_role": "user",
  "new_role": "editor",
  "result": "success"
}
```

This provides useful accountability.

---

# 🧾 Audit Trail Properties

Good audit records should generally be:

### Accurate

The event should represent what actually happened.

### Timestamped

Time information is essential for reconstruction.

### Attributable

The system should identify the actor where appropriate.

### Protected

Attackers should not be able to easily modify or delete evidence.

### Searchable

Security teams should be able to investigate events efficiently.

### Retained

Important records should be kept according to operational, legal, and organizational requirements.

---

# ⚠️ Protecting Logs

Logs themselves are valuable targets.

An attacker may try to:

```text
Delete logs
Modify logs
Flood logs
Forge log entries
Disable logging
Access sensitive logs
```

Therefore, organizations may use:

```text
Centralized logging
Access controls
Immutable/WORM storage where appropriate
Integrity monitoring
Restricted permissions
Backup
Retention policies
```

# 5️⃣ Security Visibility

## 👁️ What Is Security Visibility?

**Security visibility** means having enough trustworthy information about systems, users, applications, and network activity to detect and investigate security events.

Think of it as:

> **Can the security team actually see what is happening?**

---

# 🌐 Visibility Layers

A web environment can generate telemetry from multiple sources:

```text
                    Security Visibility
                           │
       ┌───────────────────┼───────────────────┐
       ↓                   ↓                   ↓
   Application           Server              Network
      Logs                Logs                Logs
       │                   │                   │
       └───────────────────┼───────────────────┘
                           ↓
                     Log Collection
                           ↓
                         SIEM
                           ↓
                  Detection & Alerting
```

---

# 📊 Common Security Telemetry

| Source              | Useful Information               |
| ------------------- | -------------------------------- |
| Application logs    | User actions, application events |
| Access logs         | HTTP requests                    |
| Error logs          | Failures and exceptions          |
| Authentication logs | Login activity                   |
| Firewall logs       | Network connections              |
| DNS logs            | Domain queries                   |

# 🧩 SIEM

## What Is SIEM?

**SIEM** stands for:

> **Security Information and Event Management**

A SIEM collects and analyzes security-related events from multiple sources.

Conceptually:

```text
Application Logs ─────┐
Server Logs ──────────┤
Firewall Logs ────────┤
DNS Logs ─────────────┤
Endpoint Logs ────────┤
Authentication Logs ──┤
                      ↓
                    SIEM
                      ↓
             Correlation / Rules
                      ↓
                    Alert
                      ↓
                   Analyst
```

This connects directly to your earlier **SOC and security automation** topics.

---

# 🔗 Log Correlation

A single event might not be suspicious.

For example:

```text
Failed login
```

could simply mean:

```text
User forgot password
```

But:

```text
20 failed logins
      +
Successful login
      +
New IP address
      +
Privilege change
```

is much more interesting for investigation.

This is called **correlation**.

---

# 🚨 Example Security Detection

Imagine the following:

### Event 1

```text
20 failed login attempts
```

### Event 2

```text
Successful login
```

### Event 3

```text
New session created
```

### Event 4

```text
Account privilege changed
```

A detection system could correlate:

```text
Failed Logins
      ↓
Successful Login
      ↓
Privilege Change
      ↓
HIGH-PRIORITY INVESTIGATION
```

Again, this is an investigative signal—not automatic proof of compromise.

---

# ⏱️ Time Synchronization

Imagine three systems report:

```text
Server A → 10:01:10
Server B → 10:05:42
Server C → 09:58:21
```

If their clocks are inaccurate, reconstructing the timeline becomes difficult.

Security environments therefore commonly use time synchronization mechanisms such as:

```text
NTP
```

Accurate timestamps are extremely important for:

* Incident response
* Log correlation
* Forensics
* Investigation

# 🧠 Detection vs Monitoring

These terms are related but different.

### Monitoring

Continuously observing systems.

```text
CPU
Memory
Requests
Errors
Logins
Network traffic
```

### Detection

Using observed data to identify potentially suspicious conditions.

```text
Many failed logins
       ↓
Detection rule
       ↓
Alert
```

### Response

Taking action after detection.

```text
Alert
 ↓
Investigate
 ↓
Contain
 ↓
Remediate
```

# ⚠️ Logging vs Monitoring

Don't confuse these concepts.

| Logging                | Monitoring                    |
| ---------------------- | ----------------------------- |
| Records events         | Observes events continuously  |
| Creates evidence       | Looks for conditions/patterns |
| Historical information | Often near-real-time          |
| Helps investigation    | Helps detection               |
| Passive record         | Active analysis               |

Example:

```text
Logging:
"User failed login at 10:20."

Monitoring:
"Alert: 15 failed logins occurred in 2 minutes."
```
